# uGame WorldGraph

Introduced in **v0.0.30**.

## Purpose

WorldGraph separates persistent world identity and connections from Phaser scene runtime objects.

Source of world definitions:

- `data/world.json`
- loader/resolver: `src/world-graph.js`
- renderer/runtime zone builder: `src/zone-system.js`

`ZoneSystem` no longer owns the authoritative zone list or hard-coded target zone links.

## Stable ids

Current stable zone ids:

- `zone-001`
- `zone-002`
- `zone-003`
- `zone-004`

Current stable transition ids:

- `transition-zone-001-right-to-zone-002-left`
- `transition-zone-002-left-to-zone-001-right`
- `transition-zone-001-bottom-to-zone-003-top`
- `transition-zone-003-top-to-zone-001-bottom`
- `transition-zone-002-bottom-to-zone-004-top`
- `transition-zone-004-top-to-zone-002-bottom`
- `transition-zone-003-right-to-zone-004-left`
- `transition-zone-004-left-to-zone-003-right`

Stable ids are technical identity. Visible names such as `Zone 1` may change later without changing save identity.

Existing interactable ids are intentionally unchanged in this step so saves created in v0.0.29 continue to recognize already-used one-time objects. Interactable identity is handled separately by the later Interactable 2.0 stage.

## Save compatibility

v0.0.29 could save numeric zone ids `1` and `2`.

`data/world.json` keeps them as `legacyIds`. WorldGraph resolves them to `zone-001` and `zone-002`. When the restored zone emits `zone:enter`, the existing Game State stores the canonical stable string id and SaveSystem writes it back automatically.

The Game State schema remains version 1 because the existing schema already allowed string zone ids; this is an identity migration, not a structural save-schema change.

## World data shape

`data/world.json` contains:

- `schemaVersion` — world-definition schema version;
- `start` — default zone and entry;
- `zones` — zone definitions, entries, rules, walls and current interactable definitions;
- `transitions` — stable links between zones.

A transition owns:

- stable `id`;
- `from.zoneId` and boundary `side`;
- `to.zoneId` and `entryId`;
- trigger and sound data.

Portals generated by `ZoneSystem` point to the transition id rather than embedding a second copy of the target zone connection.

## Runtime flow

1. `main.js` loads the saved Game State.
2. WorldGraph loads `data/world.json`.
3. Saved legacy/canonical zone id is resolved to a stable id.
4. `ZoneSystem` builds the resolved zone.
5. Crossing a portal activates its transition id.
6. WorldGraph resolves that transition to the target zone and entry.
7. `zone:enter` persists the canonical stable zone id.


## Responsive viewport since v0.0.56

The authored prototype layout remains a 960×540 **base coordinate space**, but the browser viewport is no longer forced into a 16:9 letterbox.

`ResponsiveViewportSystem` keeps one uniform camera scale based on available height. Extra horizontal screen space becomes extra world width rather than stretched pixels.

`ZoneSystem` therefore:

- centers legacy 960-wide authored coordinates inside the responsive world;
- keeps top/bottom authored content centered;
- anchors left/right entry points and portal boundaries to the real responsive edges;
- rebuilds walls/interactables on viewport-width changes;
- emits `zone:relayout` so dynamic Event Spots can remap too.

This preserves player/NPC/Vision proportions while allowing wide displays to show more world.

Zone definitions also now carry prototype `biome` and `isCity` fields used by `GroundTextureSystem`. These visual fields do not change stable zone identity or transition identity.

## Scope of v0.0.30

This stage does **not** add new gameplay content. It only changes world architecture and identity.

It deliberately does not implement:

- procedural world generation;
- dynamic portal rotation;
- fast travel UI;
- NPC-driven travel;
- world simulation;
- Interactable 2.0;
- combat.

The graph format leaves room for those later without making them part of this release.

## Manual QA

Use a save created by v0.0.29 if available.

1. Update and launch v0.0.30 without clearing the save.
2. Confirm the game opens in the previously saved zone.
3. The footer zone status should now include `zone-001` or `zone-002`.
4. Cross from Zone 1 to Zone 2 and back; entry sides should remain correct.
5. Reload the page in Zone 2; it should reopen in Zone 2.
6. Previously collected one-time resources/chests must remain used.
7. `9099` should continue to report a valid save.

If this passes, WorldGraph + stable world ids can be marked QA-complete and development can proceed to Interactable 2.0.
