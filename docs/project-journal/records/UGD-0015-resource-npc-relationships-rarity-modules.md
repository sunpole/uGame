# UGD-0015 — Ресурсные NPC, отношения, редкость и каскад модулей

Дата: 2026-10-06  
Тип: system  
Статус: discussing  
Flags: needs-prototype, needs-test, needs-calculation, needs-lore  
Теги: npc, relationships, idle, process, resources, skills, rarity, modules, quests, analytics, lore

## Контекст

Ресурсный Event не обязательно должен выглядеть как безличный блок/жила/объект. Рабочая идея — часть ресурсных Event представлять через человекоподобных NPC-специалистов, которые находятся возле места события и могут немного перемещаться вокруг него.

NPC становится не просто диалоговой кнопкой, а входной точкой в целое игровое направление: добыча, отношения, Idle/Process, аналитика, дерево навыков, квесты, события и другие модули.

## Базовая цепочка

```text
Dynamic Event Spot
        ↓
появился ресурсный NPC
        ↓
NPC Interaction
        ↓
доступный в этой встрече набор модулей
        ↓
Dialogue / Process / Quest / Analytics / Skill Tree / Events / ...
        ↓
отношения + ресурсы + mastery + открытия
        ↓
постоянный прогресс NPC/направления
```

NPC не должен содержать всю эту логику внутри себя. Он является точкой входа, а сами функции остаются отдельными модулями.

## Пример набора модулей

Для обсуждения используется условный набор из 6 модулей:

1. Добыча / Process / Idle;
2. Разговор / Dialogue;
3. Квесты;
4. Аналитика направления;
5. Дерево навыков;
6. Мероприятия / специальные Event.

В будущем модулей может стать 8, 10 и больше. Система не должна зависеть от фиксированного числа 6.

### Добыча — обязательный модуль

Модуль добычи присутствует у ресурсного NPC всегда.

```text
P(Добыча доступна) = 100%
```

Остальные доступные модули выбираются из пула без повторов.

## Редкость NPC / встречи

Используется уже знакомый проекту профиль вероятностей:

| Tier | Шанс | Доступных модулей | КПД взаимодействия |
| --- | ---: | ---: | ---: |
| T1 / normal | 80% | 2–3 | ×1.00 / +0% |
| T2 / rare | 15% | 3–4 | ×1.20 / +20% |
| T3 / magic | 3.5% | 4–5* | ×1.40 / +40% |
| T4 / unique | 1.5% | все модули | ×1.60 / +60% |

`*` В обсуждении изначально звучало 4–6 модулей для T3. Это оставлено открытым вопросом: если полный набор должен быть эксклюзивом 1.5%-Tier, предпочтительнее 4–5. Если T3 иногда может показывать всё, можно оставить 4–6.

Количество модулей сначала определяется по Tier, затем Добыча добавляется обязательно, а оставшиеся позиции случайно выбираются из доступного пула.

Пример при 6 модулях:

```text
T1 → Добыча + ещё 1–2 случайных
T2 → Добыча + ещё 2–3 случайных
T3 → Добыча + ещё 3–4 случайных
T4 → все 6
```

## КПД NPC

Редкость также даёт временный множитель эффективности текущего взаимодействия с NPC:

```text
T1 = ×1.00
T2 = ×1.20
T3 = ×1.40
T4 = ×1.60
```

Смысл: более редкая встреча не только даёт больше доступных функций, но и делает работу с этим NPC эффективнее.

Точная область применения КПД пока не утверждена. Возможные варианты:

- Relationship XP;
- прогресс связанного Process/Idle;
- прогресс mastery направления;
- отдельные квестовые/тренировочные действия;
- комбинация этих величин.

Важно не применять этот коэффициент автоматически ко всем наградам игры, пока не проверен баланс.

## Отношения с NPC

У NPC предполагается постоянное состояние отношений с игроком:

```text
npcId
relationshipXp
relationshipLevel
availableSkillPoints
unlockedNpcSkills
history / flags
```

Отношения должны расти за значимые действия, а не за бесконечное повторение кнопки «Поговорить». Возможные источники роста:

- выполнение квеста;
- завершение добычи/Process;
- помощь NPC;
- одноразовые значимые ветки Dialogue;
- участие в мероприятии;
- выполнение специального запроса NPC.

## Личное дерево развития

У каждого направления/NPC может быть собственное дерево навыков и собственные очки развития.

Пример для направления Камня:

```text
Добыча
├─ скорость/эффективность Process
├─ качество результата
└─ новые варианты добычи

Логистика
├─ переносимый вес
├─ stack limit
└─ дополнительные resource slots

Развитие направления
├─ влияние на персонажа
├─ новые свойства навыков
└─ новые Event / Process / доступы
```

Это пока пример структуры, а не утверждённое дерево.

## Аналитика направления

NPC может открывать профиль/аналитический экран своего направления.

Для Камня такой экран в будущем может показывать:

- сколько добыто;
- текущий ранг/mastery;
- активный бонус/резонанс;
- текущий КПД;
- прогресс до следующего уровня;
- открытые навыки;
- историю/статистику связанных Process.

Идея: аналитика распределяется по направлениям/NPC, а не обязательно собирается в один глобальный огромный экран.

## Связь с Idle / Process

NPC должен естественно соединять active и idle части.

Пример:

```text
встретил NPC
↓
Dialogue / предложение работы
↓
запустил Process добычи
↓
Process работает во времени / offline
↓
получил ресурс
↓
растут отношения + mastery направления
↓
открываются новые модули/навыки/возможности
```

## 30-минутный цикл

Рабочая связь с текущими Dynamic Event Spots:

- ресурсный NPC живёт в активном Event примерно 30 минут;
- возле точки спавна он может иметь небольшой roaming/idle movement;
- по окончании Event слот пересчитывается;
- при следующем появлении снова рассчитывается Tier и доступный набор модулей;
- NPC/Event может исчезнуть, но постоянные отношения и прогресс не должны стираться.

## Постоянная личность и временный Event

Ключевая идея — разделить:

```text
ПОСТОЯННОЕ
личность NPC
отношения
уровень
дерево навыков
история

ВРЕМЕННОЕ
текущий spawn
Tier/редкость встречи или выбранного NPC
набор доступных модулей
КПД текущей встречи
таймер Event
```

Точная модель Tier пока не утверждена окончательно.

### Вариант A — Tier принадлежит встрече

Один и тот же NPC в разные появления может иметь разную редкость/КПД/набор модулей.

### Вариант B — Tier принадлежит самому NPC

NPC имеет постоянную градацию. Каждые 30 минут система сначала бросает 80/15/3.5/1.5%, затем выбирает/спавнит NPC соответствующего Tier. Игрок со временем учится узнавать редких персонажей по имени.

Для будущего ЛОРа вариант B выглядит особенно сильным, но пока он остаётся гипотезой, а не утверждённым решением.

## Lore / Presentation layer

Пока ЛОР и режиссура мира не определены, механика должна хранить нейтральный Tier, а художественное представление добавляться позже.

Возможный технический слой:

```text
npcTier: 1 | 2 | 3 | 4
displayName
title
portrait
dialogueStyle
loreId
```

После появления ЛОРа Tier можно представить как:

- звание: младший / опытный / старший / мастер;
- разные постоянные имена;
- имя + звание;
- любую другую внутриигровую иерархию.

Пример с именами «Августин», «Леонид» и т.п. был только иллюстрацией идеи запоминаемых персонажей и не считается частью ЛОРа.

## Почему идея может работать

Она объединяет уже обсуждённые части uGame:

```text
Dynamic Event
→ NPC
→ Dialogue
→ Relationship
→ случайный набор модулей
→ Process / Idle
→ Resource
→ Analytics / Skill Tree
→ Character / World progression
```

Редкость при этом влияет не только на размер награды, а на богатство текущей игровой возможности.

## Риски

- слишком много обязательных систем на одном NPC может перегрузить интерфейс;
- если редкий Tier слишком сильно ускоряет всё, игроки могут начать ждать только 1.5%-NPC;
- если нужный модуль слишком редко появляется, прогресс может ощущаться заблокированным RNG;
- если отношения качаются простым спамом Dialogue, система потеряет смысл;
- если каждый NPC имеет уникальную огромную ветку, объём контента быстро станет неподъёмным;
- если Tier будет одновременно и личностью, и случайным состоянием встречи, игроку может быть непонятно, что именно редкое.

## Минимальный будущий прототип

После отдельного подтверждения можно начать с одного направления — Камня:

```text
1 ресурсный NPC
6 условных модулей
Добыча всегда
Tier roll 80/15/3.5/1.5
случайный набор доступных модулей
КПД ×1.00 / ×1.20 / ×1.40 / ×1.60
persistent relationship
1 простой Process
1 маленькое дерево навыков
1 экран аналитики
```

Цель прототипа — проверить не объём контента, а ощущение от каскада возможностей через одну встречу.

## Открытые вопросы перед реализацией

1. T3 показывает 4–5 модулей или 4–6?
2. Tier принадлежит конкретному NPC навсегда или рассчитывается для каждой встречи?
3. На какие именно величины действует NPC КПД?
4. Может ли игрок всегда просматривать уже изученное дерево/аналитику, даже если соответствующий модуль не выпал в текущем spawn?
5. Как именно начисляются Relationship XP и skill points?
6. Можно ли перераспределять очки дерева NPC?
7. Один NPC = одно ресурсное направление или в будущем возможны смешанные специализации?

## Статус

Это зафиксированная **идея/рабочая гипотеза**, а не окончательно принятое правило и ещё не реализованная система.
