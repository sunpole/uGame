# UGD-0015 — Ресурсные NPC, отношения, редкость и каскад модулей

Дата: 2026-10-06  
Тип: system  
Статус: discussing  
Flags: needs-prototype, needs-test, needs-calculation, needs-lore, needs-scope-decision  
Теги: npc, relationships, idle, process, resources, skills, rarity, modules, quests, analytics, lore, character-progression

## Контекст

Рабочая идея: ресурсный Event может быть представлен не безличным блоком/жилой, а человекоподобным NPC-специалистом, который находится возле места события и может немного перемещаться рядом с точкой появления.

NPC становится входной точкой в целое ресурсное направление: добыча/Process, Dialogue, Quests, аналитика, дерево развития персонажа, мероприятия и другие модули.

Система пока не реализована. Эта запись фиксирует согласованные части и отдельно оставляет нерешённые вопросы перед кодом.

## Уже подтверждённые части

- Для примера используется 6 модулей, но архитектура не должна зависеть от числа 6; позже их может стать 8, 10 и больше.
- `Добыча / Process / Idle` у ресурсного NPC доступна всегда.
- Остальные модули текущей встречи выбираются случайно из пула без повторов.
- Рабочий rarity profile NPC использует шансы `80% / 15% / 3.5% / 1.5%`.
- T1 показывает 2–3 модуля, T2 — 3–4, T3 — **4–6**, T4 — **все модули гарантированно**.
- T3 может случайно показать полный набор. Эксклюзив T4 — не сам факт возможности увидеть все модули, а **100% гарантия полного набора и максимальный коэффициент эффективности**.
- Коэффициенты текущей встречи: `×1.00 / ×1.20 / ×1.40 / ×1.60`.
- NPC может иметь постоянные имя, звание, профессию, тип, Tier и другие данные; финальные имена/звания зависят от будущего ЛОРа.
- **Развивается персонаж игрока, а не NPC.** Улучшения добычи, переносимости, stack, mastery, skill-эффекты и другие игровые усиления принадлежат прогрессии конкретного персонажа игрока.
- У разных игроков собственные состояния отношений, прогрессии и изученных навыков даже при взаимодействии с одной и той же мировой NPC-личностью.
- NPC предоставляет доступ к возможностям/веткам/обучению; его definition не хранит персональный прогресс конкретного игрока.

## Базовая цепочка

```text
Dynamic Event Spot
        ↓
roll / выбор ресурсного NPC
        ↓
NPC Encounter
        ↓
обязательная Добыча + случайный набор остальных модулей
        ↓
Dialogue / Process / Quest / Analytics / Skill Tree / Events / ...
        ↓
отношения player↔NPC + ресурсы + mastery + character progression
        ↓
постоянное состояние конкретного персонажа игрока
```

NPC не должен содержать всю игровую логику внутри себя. Он является точкой входа, а функции остаются отдельными модулями.

## Пример набора модулей

Условный стартовый набор:

1. Добыча / Process / Idle;
2. Разговор / Dialogue;
3. Квесты;
4. Аналитика направления;
5. Дерево развития;
6. Мероприятия / специальные Event.

Это контентный пример, а не фиксированный API.

## Редкость NPC / встречи

| Tier | Шанс | Доступных модулей | Коэффициент встречи |
| --- | ---: | ---: | ---: |
| T1 / normal | 80% | 2–3 | ×1.00 / +0% |
| T2 / rare | 15% | 3–4 | ×1.20 / +20% |
| T3 / magic | 3.5% | 4–6 | ×1.40 / +40% |
| T4 / unique | 1.5% | все модули гарантированно | ×1.60 / +60% |

При 6 модулях:

```text
T1 → Добыча + ещё 1–2 случайных
T2 → Добыча + ещё 2–3 случайных
T3 → Добыча + ещё 3–5 случайных
T4 → все 6 гарантированно
```

Количество модулей и диапазоны должны быть data-driven, чтобы позже можно было менять общий пул без переписывания системы.

## Коэффициент эффективности текущей встречи

Рабочие значения:

```text
T1 = ×1.00
T2 = ×1.20
T3 = ×1.40
T4 = ×1.60
```

Это **локальный коэффициент взаимодействия с текущим NPC/Encounter**, а не автоматически тот же показатель, что глобальный `КПД`, `daily efficiency` или `Импульс` из UGD-0001 / UGD-0005 / UGD-0012.

Точная область применения локального коэффициента пока не утверждена. Кандидаты:

- Relationship XP;
- прогресс Process/Idle;
- mastery ресурсного направления;
- training / skill progression;
- отдельные квестовые действия.

Не принято, должен ли этот коэффициент менять количество физического ресурса/Reward напрямую.

## Четыре разных слоя данных

Чтобы будущая MMORPG-архитектура не смешивала общий мир и персональный прогресс, данные нужно разделять минимум на четыре слоя.

### 1. NPC Definition — общий контент мира

Описывает, **кто существует в мире**, и одинаков для всех игроков:

```text
npcId
displayName / nameKey
title / titleKey
professionId
specializationId / resourceDirectionId
npcType
tier
factionId
homeRegionId
modulePool[]
guaranteedModules[]
dialogueProfileId
relationshipProfileId
analyticsProfileId
skillTreeTemplateIds[]
processProfileIds[]
spawnPoolIds[]
movementProfileId
appearanceId / portraitId
loreId
requirements[]
tags[]
enabled
```

Финальные имена, звания, фракции и профессии сейчас являются полями структуры, а не утверждённым ЛОРом.

### 2. NPC Encounter — текущее появление

Описывает временную встречу:

```text
encounterId
npcId
zoneId
eventSpotId
spawnedAt
expiresAt
activeModules[]
moduleCount
efficiencyMultiplier
currentQuestIds[]
currentProcessOfferIds[]
temporaryFlags[]
```

Если Tier в итоге будет постоянным свойством NPC, Encounter читает его из NPC Definition. Если Tier окажется свойством встречи, Encounter хранит результат roll. Этот выбор ещё не закрыт.

### 3. Character ↔ NPC Relationship State — персональные отношения

Это состояние конкретного персонажа игрока относительно конкретного NPC:

```text
characterId
npcId
relationshipXp
relationshipLevel
encountersCount
completedNpcQuestIds[]
dialogueFlags[]
firstMetAt
lastMetAt
specialFlags[]
```

Отношения не должны расти от бесконечного спама кнопки Dialogue. Источники роста — значимые действия: квесты, Process, помощь, одноразовые диалоги, мероприятия и специальные запросы.

Точный scope отношений для нескольких персонажей одного аккаунта ещё требует отдельного решения: `character` или `account`.

### 4. Character Resource / Skill Progression — развитие персонажа

Все реальные улучшения принадлежат персонажу игрока:

```text
characterId
resourceDirectionId
mastery
activeResonance
skillPointsEarned
skillPointsSpent
unlockedSkillNodes[]
processUnlocks[]
carry / stack / resource-slot modifiers
other character modifiers
```

NPC/направление может определять **шаблон дерева**, доступные ветки или условия обучения, но изученные узлы и полученные эффекты принадлежат Character State.

## Дерево развития

Изначальная идея «у каждого NPC своя ветка» сохраняется как возможный **контентный шаблон**, но не как место хранения прогрессии.

Есть две ещё не разведённые модели:

```text
A. NPC-specific tree template
каждый NPC предлагает свою ветку/набор узлов
→ эффекты записываются в персонажа игрока

B. Resource-direction tree
несколько NPC направления Камня открывают разные части одного Stone Tree
→ эффекты также записываются в персонажа игрока
```

Какую модель выбрать — открытый вопрос аудита.

Пример возможных веток Камня:

```text
Добыча
├─ скорость/эффективность Process
├─ качество результата
└─ новые варианты добычи

Логистика
├─ переносимый вес
├─ stack limit
└─ дополнительные resource slots

Развитие направления
├─ влияние на персонажа
├─ новые свойства навыков
└─ новые Event / Process / доступы
```

## Аналитика направления

NPC может открывать профиль/аналитический экран своего направления. Возможные данные:

- сколько добыто;
- mastery / ранг;
- active resonance;
- локальная эффективность текущей встречи;
- будущая daily efficiency;
- прогресс до следующего уровня;
- изученные skill nodes;
- история связанных Process.

Важно визуально и терминологически не смешивать локальный NPC multiplier с глобальным/дневным КПД.

## Связь с Idle / Process

```text
встретил NPC
↓
Dialogue / предложение работы
↓
запустил Process добычи
↓
Process живёт во времени / offline
↓
получил ресурс
↓
растут отношения + mastery/character progression
↓
открываются новые возможности
```

Нужно отдельно решить, продолжает ли уже запущенный Process работать после исчезновения 30-минутного NPC Encounter.

## 30-минутный цикл

- ресурсный NPC связан с Dynamic Event Slot примерно на 30 минут;
- возле точки появления возможен небольшой roaming/idle movement;
- после окончания Event слот пересчитывается;
- новый Encounter получает новый набор доступных модулей;
- NPC/Event может исчезнуть, но персональный прогресс игрока не стирается.

Способ выбора Tier/NPC после пересчёта пока не закрыт окончательно.

## Tier и будущий Lore layer

Пока ЛОР не определён, механика хранит нейтральные поля Tier/identity.

Будущий presentation layer может использовать:

- имя;
- звание;
- профессию;
- фракцию;
- портрет/внешность;
- характер/стиль речи;
- происхождение/регион;
- уникальные lore tags.

Игроки потенциально смогут со временем узнавать сильных/редких NPC по имени и званию. Это аргумент в пользу постоянного Tier у личности, но окончательное правило пока не принято.

## Пересечение с текущими системами

- `UGD-0010`: NPC Encounter естественно выступает Event → modules entry point.
- `UGD-0011`: ресурсная прогрессия уже определена как развитие **персонажа**, что согласуется с текущим уточнением.
- `UGD-0012`: `daily efficiency` остаётся отдельным коэффициентом времени и не должен автоматически сливаться с NPC multiplier.
- `UGD-0013`: текущий 30-минутный Dynamic Event слой может стать носителем NPC Encounter.
- `UGD-0014`: container modifiers могут получать значения из Character Skill Progression, а не из изменяемого состояния NPC.
- `UGD-0001`: Внимание остаётся account-bound и не должно случайно стать character-bound из-за NPC-системы.

## Риски

- нужный модуль может слишком редко появляться и ощущаться как RNG-блокировка;
- ×1.60 может стать настолько выгодным, что игроки начнут игнорировать T1/T2;
- несколько независимых rarity-roll с одинаковыми процентами могут быть непонятны и ошибочно связаны в коде;
- локальный NPC multiplier и global/daily КПД могут быть перепутаны;
- огромные уникальные деревья на каждого NPC могут создать неподъёмный объём контента;
- если Process обрывается вместе с 30-минутным Encounter, Idle может превратиться в раздражающий таймер;
- если все Resource Events заменить NPC без альтернатив, мир может потерять разнообразие объектов.

## Минимальный будущий прототип

После закрытия вопросов аудита можно начать с одного ресурсного направления:

```text

1 ресурсное направление
6 условных модулей
Добыча всегда

2–3 / 3–4 / 4–6 / all
×1.00 / ×1.20 / ×1.40 / ×1.60

```

## Открытые вопросы перед закреплением

1. Tier — постоянное свойство NPC Definition или временный roll Encounter?
2. NPC Tier roll независим от Zone Quality и Reward Rarity или должен быть связан с одним из них?
3. Что именно умножает локальный коэффициент `×1.00…×1.60`?
4. Skill Tree template принадлежит конкретному NPC или всему ресурсному направлению?
5. Relationship State принадлежит персонажу или аккаунту, если на одном аккаунте будет несколько персонажей?
6. Можно ли всегда просматривать уже изученную аналитику/дерево, когда соответствующий модуль не выпал в текущем Encounter?
7. Продолжает ли уже запущенный Process работать после despawn NPC?
8. Все Resource Events должны стать NPC или NPC является только одним из вариантов ресурсного Event?
9. Один NPC всегда относится к одному resourceDirection или позднее допустимы смешанные специализации?
10. Можно ли перераспределять Character skill points?
